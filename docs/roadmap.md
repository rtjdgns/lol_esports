# 로드맵 (스택 제안, 최종 확정 아님)

## 스택
| 계층 | 선택 | 확정 시점 |
|---|---|---|
| 코어 | Python (수집 어댑터, 스키마, 규칙 엔진, 시나리오 계산기) | 확정 |
| 저장소 | SQLite로 시작 | 확정 |
| 규칙 | YAML/JSON 규칙 파일 | 확정 |
| 테스트 | pytest | 확정 |
| API 서버 | FastAPI (추정) | 4단계 |
| 스케줄러 | 서버 내 스케줄러 또는 cron | 5단계 |
| 푸시 | 텔레그램 봇 → FCM/APNs | 3단계 → 6단계 |
| 앱 | Flutter 또는 React Native(Expo) | 6단계 |
| 호스팅 | 항상 켜진 서버 (무료·저가 조건 확인 필요) | 5단계 |

## 단계
1. 데이터 소스 검증: 인증, 시리즈 스코어, Bo, 단계, 순위, 로스터 필드 확인. 산출물 `docs/api_findings.md`. 막히면 보조 소스(PandaScore 등)로 전환하고 어댑터만 교체.
2. 코어 데이터 모델과 수집기: Match, Series, Team, Standing, RosterEntry 스키마, 어댑터 인터페이스, SQLite 저장, 팀 별칭(한글·영문) 정규화. 완료 기준: 터미널에서 "오늘 경기 목록"이 한국어 팀명으로 출력.
3. 시리즈 상황 + 알림 로직(텔레그램 봇): 남은 승수 계산, 팀 팔로우, 상태 변화 감지, 종류별 알림 설정. 완료 기준: 경기 하나를 시작부터 종료까지 알림으로 추적.
4. 규칙 엔진 + 순위 경우의 수: 규칙 파일 설계, 시나리오 계산기, 확정/탈락/조건부 판정, FastAPI JSON 계층. 테스트는 정답이 알려진 과거 대회 고정 입력.
5. 서버 배포 + 스케줄러: 호스팅 선택, 폴링 주기, 로그·실패 알림, 키 보관. 완료 기준: 며칠 무인 운영.
6. 모바일 앱: 프레임워크 확정, FCM/APNs 연동. 텔레그램은 백업 채널.
7. 확장: 월즈 대진 고도화, 중요 경기 배지, ICS, 스포일러 방지, 로스터 diff, 선수 팔로우, 소식 피드.

## 순서 변경 (2026-10-16)
알림은 서버 스케줄러(5단계)와 라이브 데이터 확인이 선행돼야 의미가 있어 뒤로 미뤘다. 현재 순서: ① 시리즈 문구·팀 팔로우를 CLI에 연결(완료) → ② 4단계 경우의 수(스위스 우선) → ③ 라이브 데이터 수집(플레이-인 중 확인 완료) → ④ 알림을 서버 배포와 함께.

## 대회 유형별 계산 (2026-10-16 결정)
- 정규리그(LCK 등): 순위 경우의 수. 확정/탈락/조건부 판정, 필요 승수, 타이브레이커. 순위 경쟁이 있는 유일한 유형.
- 국제대회(월즈 등): 순위 경쟁이 없다. 대진 경우의 수(다음 상대 후보, 진출 경로)와 우승 경우의 수(우승까지의 경로)를 보여준다.
- 스위스는 순위 비교가 아니라 3승/3패 선도달이므로 팀 단위 상태기계로 충분하다(월즈 2025 33경기 재생으로 검증: 재대결 0, 결정전만 Bo3, 최종 3-0 2팀·3-1 3팀·3-2 3팀).
- 토너먼트 대진: `previousMatchIds`가 비어 있어 경기 id 순서로 복원한다. 인접한 두 경기의 승자가 다음 라운드 한 경기로 이어진다(월즈 2025 7경기에서 확인, 단일 대회라 추정). 슬롯 순서는 신뢰하지 않는다.
- 우승 경우의 수는 경로 열거까지만 한다. 확률은 별도 모델이 필요하고 가정을 명시해야 하므로 제외.

## 결정 사항
- 원본(Raw) 저장: SQLite 확정에 맞춰 `raw_responses` 테이블(엔드포인트, 파라미터, 수집 시각, 본문)에 저장. 이전에 제안한 파일 저장은 철회. `data/raw_samples/`는 테스트 고정 입력으로만 유지.
