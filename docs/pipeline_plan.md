# 파이프라인 계획 (뼈대 우선)

한 번에 하나의 단계만 구현하고, 각 단계의 산출물을 확인한 뒤 다음으로 넘어간다.

## 현재 위치
- 0단계 API 검증: 완료 (`docs/api_findings.md`)
- 1단계 수집 가능 데이터 목록: 완료 (`docs/data_inventory.md`, 자동 생성)
- 이전에 만든 `models/`, `collectors/`, `engine/`은 시안이다. 2단계 이후에 다시 검토하고 필요하면 고친다.

## 수집 대상 (확인됨)
| 엔드포인트 | 얻는 것 | 호출 시점 |
|---|---|---|
| getLeagues | 리그 id, slug, 지역 | 드묾 |
| getTournamentsForLeague | 대회 id, slug, 기간 | 일 단위 |
| getSchedule | 경기 목록, 상태, Bo, 세트 승수, 단계명, 팀 전적 | 시간 단위, 경기 중 짧게 |
| getStandings | 단계/섹션 구조, 대진 트리(previousMatchIds) | 경기 종료 시 |
| getEventDetails | 세트별 정보(진영, VOD) | 필요 시 |
| getTeams | 팀, 선수 | 일 단위 |
| getLive | 생중계 이벤트 | 경기 중 (구조 미확인) |

## 전처리에서 처리해야 할 것 (원본 샘플에서 확인)
1. TBD 팀: getSchedule 80건 중 38건이 `name/code = TBD`이고 `result`, `record`가 null이다 (예정 경기, 대진 미확정). 팀 id가 없으므로 경기 단위 식별은 match id로만 가능하다.
2. `result.outcome`은 완료 전 null.
3. `match.flags`: `hasVod`, `isSpoiler`가 있다. 스포일러 방지 모드의 입력이 될 수 있다 (의미는 추정).
4. 시각은 UTC 문자열. 표시 시 KST 변환.
5. 단계 구분은 `blockName`(한국어 문자열)뿐이다. 언어를 바꾸면 값이 달라지므로 기준 키로 쓰면 안 된다. getStandings의 `stages[].slug`(play_ins/swiss/knockouts)와 매핑 필요.
6. getSchedule 한 응답에 과거 완료분과 미래 예정분이 섞여 있고 페이징 토큰(older/newer)이 있다.
7. 팀 id가 엔드포인트마다 다를 수 있는지 미확인 (getSchedule 팀에는 id가 없다).

## 단계
| 단계 | 내용 | 산출물 | 완료 기준 |
|---|---|---|---|
| 2 | 원본 저장(Raw) | 호출 시각·파라미터와 함께 응답을 그대로 저장, 재호출 가능 | 같은 호출을 반복해도 덮어쓰지 않고 이력이 남는다 |
| 3 | 정규화 | Raw → 공통 스키마 변환, TBD 처리, 시간대, 단계 키 매핑 | 저장된 샘플 전체가 오류 없이 변환되고 필드 누락이 집계된다 |
| 4 | 검증 | 값 범위·일관성 검사 (세트 승수 ≤ 과반, 완료 경기엔 승자 존재 등) | 위반 건수 리포트 |
| 5 | 저장 | SQLite 테이블, 업서트 | 재실행해도 중복 없음 |
| 6 | 변경 감지 | 이전 상태와 비교해 이벤트 생성 (시작, 세트 종료, 시리즈 종료) | 알림의 입력이 된다 |
| 7 | 파생 | 시리즈 상황 문구, 스위스 상태, 경우의 수 | 규칙 파일 기반 |
| 8 | 표현 | 모바일 UI, 알림, ICS | 위 단계가 안정된 뒤 |

## 합의가 필요한 것
- 2단계의 Raw 저장 위치: 파일(JSON, 날짜별 폴더) vs SQLite 한 테이블. 제안: 파일. 이유는 단순하고 diff가 쉽다.
- 호출 주기와 실행 방식: 수동 실행 스크립트로 시작, 스케줄링은 6단계 이후.
